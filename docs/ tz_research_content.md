# ТЗ: контентный слой Research API (репозиторий бота)

Предшественник `tz-admin-client.md`. Пишется **до** сайта: админка не сможет
сохранить ни прозу, ни английскую версию, пока этих полей нет в API, и написанное
пришлось бы выбрасывать.

Один шаг — один вызов Codex. Шаги идут строго по порядку, каждый оставляет
репозиторий в компилирующемся состоянии с зелёными тестами.

**Общие правила для каждого вызова:**

- Работать по `CLAUDE.md` §9. Формат правок, формат ответа, архитектура — оттуда,
  здесь не повторяются.
- Перед изменением читать существующий код, типы, `prisma/schema.prisma` и
  `docs/RESEARCH-API.md`.
- Не трогать ничего в `src/bot/**`, `src/alerts/**`, `src/notifications/**`,
  `src/content/**`.
- Env читается лениво из функций, не через `export const X = process.env.Y`
  на верхнем уровне модуля.
- `null` ≠ `0` (инвариант 5). Отсутствующее значение остаётся `null` на выходе.
- Новых зависимостей не добавлять без явного обоснования в ответе.
- После любой правки контракта — `make api-docs`; гейт — `make api-docs-check`.

---

## Зачем этот шаг существует

Спецификация движка требует: **метрики хранятся полями, а не числами внутри
текста статьи.** Разбор — это запись с типизированными полями плюс проза, в
которую числа подставляются переменными. Числа, зашитые в абзацы, нельзя
обновить, пересчитать и сравнить между разборами; движок в этом случае
невозможен в принципе.

Половина требования уже выполнена: `ResearchProtocol`, `ResearchMethodology`,
`ResearchSnapshot`, `ResearchValuation` и `ResearchTrigger` хранят числа полями,
медиана сектора пересчитывается на каждой записи и удалении. Второй половины —
прозы, привязанной к этим полям, — нет вовсе.

| Требование спецификации | Сейчас в `ResearchVerdict` |
| --- | --- |
| `body` — проза с плейсхолдерами полей | поля нет |
| `counterarguments` — обязательное, непустое | поля нет |
| `reasons[]` — 3 × `{ text, metric_ref }` | `reasons Json`, структура ничем не держится |
| `changelog[]` — что изменилось и почему | `changeReason String?`, одна строка, без локали |
| локали ru/en, переводится только проза | нет нигде |
| §3: отклонение от **опубликованного среза** | вердикт не ссылается на снимок |

Последняя строка — не косметика. Все четыре состояния страницы из §3
(`АКТУАЛЬНО`, `ДАННЫЕ ОБНОВИЛИСЬ`, `ВЕРДИКТ ПЕРЕСМОТРЕН`,
`ДАННЫЕ НЕ ПОДТВЕРЖДЕНЫ`) вычисляются относительно среза, на котором вердикт был
вынесен. Без ссылки на снимок считать не от чего.

## Решения, принятые до шагов

Каждое закрывает развилку, которую иначе пришлось бы решать по ходу и по-разному
в разных местах.

**Проза живёт в отдельной таблице по локалям, а не колонками `bodyRu`/`bodyEn`.**
Английская версия — перевод текста, а не второй разбор: у неё те же числа, те же
`metric_ref`, тот же номер версии. При колонках «перевода ещё нет» превращается в
россыпь `null` по четырём полям, и ни админка, ни публичная страница не могут
отличить «не переведено» от «переведено пустой строкой». Отдельная строка на
локаль даёт это одним фактом её существования.

**Структура причин отделена от их текста.** `metric_ref` и порядок не
локализуются — они одинаковы в обеих версиях по определению. Текст —
локализуется. Поэтому `ResearchVerdictReason` хранит ссылку на поле и позицию, а
текст лежит в локализованной записи и сопоставляется по позиции. Хранить
`metric_ref` внутри перевода означало бы, что английская версия может сослаться
на другую метрику, а это уже не перевод.

**Причин ровно три.** Так требует спецификация, и это единственное правило,
которое механически держит прозу привязанной к числам: три причины, каждая со
ссылкой на конкретное поле. «От двух до пяти» превратилось бы в «сколько
написалось», и через десять разборов ссылки исчезли бы вовсе.

**Плейсхолдеры сервер валидирует, но не подставляет.** Неизвестный плейсхолдер
отвергается при записи — битый разбор нельзя опубликовать физически. Подстановка
и формат числа — на стороне сайта: §5 требует локализовать формат на выводе, а
это уже представление, и в API ему делать нечего.

**Отдельной сущности `changelog` нет.** История вердиктов уже версионирована:
`version`, `publishedAt`, `updatedAt` и порядок по разобранным частям версии.
Вторая таблица с теми же датами разошлась бы с первой на первой же правке.
Вместо неё — локализованное `changeSummary` на каждой версии; changelog
собирается запросом к истории.

**Автоматический перевод — работа сайта, не бота.** API хранит обе версии и
флаг «переведено машиной». Провайдер перевода, его ключ и лимиты в этот
репозиторий не попадают.

## C1. Схема данных

**Цель.** Локализованная проза, структурированные причины, привязка вердикта к
срезу.

**Читать сначала:** `prisma/schema.prisma` целиком, `CLAUDE.md` §1 инвариант 3,
§5 про легаси-колонки, `docs/RESEARCH-API.md` раздел «Схема данных».

**Сделать.**

Новые enum'ы:

```prisma
enum ResearchLocale { RU EN }

enum ResearchMetricRef {
  PRICE
  CIRCULATING_SUPPLY
  TOTAL_SUPPLY
  MARKET_CAP
  FDV
  PROTOCOL_REVENUE_12M
  TOKEN_INCENTIVES_12M
  NET_REVENUE_12M
  FDV_REVENUE
  BUYBACK_ANNUAL_USD
  VAR_PCT
  EMISSIONS_12M_TOKENS
  UNLOCKS_12M_TOKENS
  SPR_PCT
  NET_TOKEN_FLOW_PCT
  SECTOR_MEDIAN_FDV_REVENUE
  FAIR_FDV
  PREMIUM_PCT
  FLOW_NEUTRAL_PRICE
  IMPLIED_REVENUE
  IMPLIED_GROWTH_X
}
```

`ResearchMetricRef` — надмножество `ResearchTriggerMetric`, но отдельный enum:
триггер описывает **вычислимое условие**, ссылка описывает **цитируемое поле**.
Слияние разрешило бы триггер на `createdAt`. Расхождение ловит юнит из C6.

Новые модели:

```prisma
model ResearchVerdictText {
  id                  String          @id @default(cuid())
  verdictId           String
  locale              ResearchLocale
  body                String
  counterarguments    String
  changeSummary       String?
  reasonTexts         Json
  isMachineTranslated Boolean         @default(false)
  createdAt           DateTime        @default(now())
  updatedAt           DateTime        @updatedAt
  verdict             ResearchVerdict @relation(fields: [verdictId], references: [id], onDelete: Cascade)

  @@unique([verdictId, locale])
}

model ResearchVerdictReason {
  id        String            @id @default(cuid())
  verdictId String
  position  Int
  metricRef ResearchMetricRef
  createdAt DateTime          @default(now())
  updatedAt DateTime          @updatedAt
  verdict   ResearchVerdict   @relation(fields: [verdictId], references: [id], onDelete: Cascade)

  @@unique([verdictId, position])
}
```

`reasonTexts` — массив из трёх строк, сопоставляемый с `position` по индексу.
Отдельная таблица на текст причины дала бы четвёртую сущность ради трёх строк.

В `ResearchVerdict` добавить:

- `snapshotId String?` и связь с `ResearchSnapshot`, `onDelete: SetNull`.
  Удалённый снимок не должен уносить вердикт — он должен лишать его опоры, и
  расчёт свежести обязан это заметить, а не показать старое число.
- связи `texts ResearchVerdictText[]` и `reasons ResearchVerdictReason[]`.

Колонку `reasons Json` **переименовать** в `legacyReasons Json?` и оставить
nullable. Прямое удаление уничтожило бы единственную копию уже написанных
обоснований до того, как их перенесут руками; колонка снимается отдельной
миграцией после переноса, и это записывается в `docs/RESEARCH-API.md` как
известный долг с датой.

Миграция:

- добавляет enum'ы, таблицы, `snapshotId`, переименовывает `reasons`;
- **не** создаёт записи `ResearchVerdictText` для существующих вердиктов:
  автоматически сгенерированная пустая проза неотличима от написанной человеком
  и опубликовалась бы молча.

**Приёмка.** `npx prisma migrate dev` применяется на чистой базе и на базе с
данными. `make typecheck` зелёный. `SELECT` по существующим вердиктам показывает
`legacyReasons` непустым, `snapshotId` — `NULL`.

## C2. Домен

**Цель.** Правила, по которым разбор считается пригодным к публикации.

**Читать сначала:** `src/research/domain/**` целиком, особенно валидацию
вердикта и `research.types.ts`.

**Сделать.** Чистые функции в `src/research/domain/`, без Prisma и без HTTP.

`parsePlaceholders(markdown): string[]` — извлекает ссылки вида
`{{snapshot.fdvRevenue}}` и `{{valuation.premiumPct}}`. Никакого рендера: функция
только называет то, что нашла.

`validateVerdictText(input)` — отвергает:

- пустые `body` или `counterarguments` (`counterarguments` обязательно и непусто
  по спецификации: разбор без контраргумента — это не разбор, а мнение);
- `reasonTexts` длиной не три или с пустой строкой;
- плейсхолдер, не соответствующий ни одному `ResearchMetricRef`.

`validateVerdictReasons(reasons)` — ровно три, позиции `1,2,3` без пропусков и
повторов, `metricRef` не повторяется: три причины со ссылкой на одно поле — это
одна причина, написанная трижды.

`metricRefValue(ref, snapshot, valuation): number | null` — единственное место,
где ссылка превращается в число. `null` остаётся `null`: подстановка нуля здесь
дала бы «Net Token Flow 0%» вместо «нет данных», а это прямо противоположные
утверждения.

Существующее правило «непустой `killersFired` ⇒ только `HIGH`» не трогать, оно
уже работает.

**Приёмка.** `make test-unit` зелёный, включая новые юниты. Тест на каждый отказ
из списка выше: он обязан быть красным, если убрать соответствующую проверку.

## C3. Репозиторий и сервис

**Цель.** Запись и чтение прозы одной транзакцией с вердиктом.

**Читать сначала:** `src/research/data/research.repository.ts`,
`src/research/research.service.ts`.

**Сделать.**

Вердикт, его причины и тексты пишутся **одной транзакцией**. Вердикт без причин
или без хотя бы одной локали не должен существовать даже на миллисекунду: между
двумя запросами публичная страница успела бы отдать разбор без обоснования.

Методы репозитория:

- `upsertVerdictText(verdictId, locale, input)` — полная замена перевода;
- `deleteVerdictText(verdictId, locale)` — снимает перевод, не трогая вердикт;
- `replaceVerdictReasons(verdictId, reasons)` — атомарная замена всех трёх;
- `findVerdictTexts(verdictId)` и батч-версия для страницы протокола.

Чтение: `findLatestVerdict` дополнительно поднимает причины и тексты **одним
батчем по списку id**, а не запросом на вердикт. История вердиктов растёт
неограниченно, размер ответа фиксирован — это уже действующий инвариант
списочных ручек, и нарушать его здесь нельзя.

Правило видимости не меняется: текущий вердикт — последний опубликованный.
Отсутствие перевода на запрошенную локаль **не** делает вердикт неопубликованным
— это разные факты, и решать, показывать ли русский текст англоязычному
читателю, будет сайт.

**Приёмка.** `make test-api` зелёный. Новый e2e: вердикт, записанный с причинами
и двумя локалями, читается целиком; удаление вердикта каскадом уносит и то и
другое; удаление снимка обнуляет `snapshotId`, но вердикт остаётся.

## C4. HTTP-слой

**Цель.** Ручки, которыми админка пишет прозу и читает её по локали.

**Читать сначала:** `src/research/http/**` целиком.

**Сделать.**

Write-ручки, под тем же `ResearchApiKeyGuard`:

```
PUT    /api/v1/protocols/:slug/verdicts/:version/reasons
PUT    /api/v1/protocols/:slug/verdicts/:version/texts/:locale
DELETE /api/v1/protocols/:slug/verdicts/:version/texts/:locale
```

`PUT` — полная замена, не слияние: на nullable-полях частичное слияние
неотличимо от «стереть значение». Исключение для `PUT /protocols/:slug` уже
описано в `docs/RESEARCH-API.md` и сюда не распространяется.

`POST` и `PUT` вердикта принимают `snapshotId`-эквивалент **естественным
ключом** — `snapshotTakenAt` в теле. Внутренние `id` наружу не уходят,
идентификатор снаружи один.

Read-ручки получают необязательный `?locale=`:

```
GET /api/v1/protocols/:slug?locale=ru
GET /api/v1/protocols/:slug/verdicts?locale=ru
```

Требования:

- дефолт `RU`; пустое значение (`?locale=`) — это незаданный параметр, а не
  ошибка (`CLAUDE.md` §4);
- перевода нет → `text: null` плюс `availableLocales: ["RU"]`. Ни `404`, ни
  молчаливого отката на русский: сайт обязан показать плашку, а не выдать чужой
  язык за свой;
- ответ несёт `snapshotTakenAt` вердикта — `null` означает, что опорный срез
  удалён;
- каждое поле DTO с описанием, каждый ответ со `schema` и непустым
  `description`: гейты в `test/unit/meta/` это проверяют и покраснеют.

**Приёмка.** `make api-docs` перегенерирована, `make api-docs-check` — `exit=0`.
`make test-api` зелёный. Swagger UI: `Try it out` с пустыми полями отвечает
`200`.

## C5. Свежесть

**Цель.** Четыре состояния страницы из §3, посчитанные на сервере.

**Читать сначала:** `src/research/domain/**`, результат C1 по `snapshotId`.

**Сделать.**

Пороги — константы домена, в одном месте:

| Метрика | Порог |
| --- | --- |
| `PROTOCOL_REVENUE_12M` | ±20% |
| `NET_TOKEN_FLOW_PCT` | ±5 п.п. |
| `SPR_PCT` | ±5 п.п. |
| `FDV_REVENUE` | ±30% |
| `PRICE` | ±40% |

Проценты и процентные пункты — разные величины, и функция сравнения обязана
знать, какая перед ней: 5% от `sprPct = 40` это 2 п.п., а не 5.

`GET /api/v1/protocols/:slug` дополнительно возвращает:

```
freshness: {
  status: "CURRENT" | "DATA_CHANGED" | "VERDICT_REVISED" | "DATA_UNVERIFIED",
  baselineTakenAt: string | null,
  deviations: [{ metricRef, baseline, current, delta, threshold }]
}
```

Правила разрешения, в порядке приоритета:

1. `sourceStatus = FAILED` у последнего снимка → `DATA_UNVERIFIED`. Показывается
   последнее известное число с датой; оценка не подставляется молча никогда.
2. Опорного среза нет (`snapshotId = null`) → `DATA_UNVERIFIED` с пустым
   `deviations`. Отсутствие базы — не «всё в порядке».
3. `updatedAt` вердикта позже `takenAt` последнего снимка → `VERDICT_REVISED`.
4. Хотя бы одно превышение порога → `DATA_CHANGED`.
5. Иначе → `CURRENT`.

Расчёт живёт на сервере, а не на сайте: пороги — часть суждения о протоколе, и
вторая копия арифметики разошлась бы с первой за квартал.

Календарь разлоков в эту версию **не** входит: сущности с датами разлоков в
схеме нет, и подпорка на глазок здесь хуже её отсутствия.

**Приёмка.** Юнит на каждое из пяти правил, включая приоритет: `FAILED` при
одновременном превышении порога обязан дать `DATA_UNVERIFIED`. E2E: снимок,
сдвинувший выручку на 25%, переводит страницу в `DATA_CHANGED`.

## C6. Гейты и контракт

**Цель.** Не дать расхождению дожить до сайта.

**Читать сначала:** `test/unit/meta/**`, `test/research-api.e2e-spec.ts`,
`test/helpers/research-query-routes.ts`.

**Сделать.**

- Юнит: каждое значение `ResearchTriggerMetric` существует в
  `ResearchMetricRef`. Enum'ы разные намеренно, но расходиться им нельзя.
- Юнит: каждый `ResearchMetricRef` разрешается функцией `metricRefValue`. Новое
  значение enum'а без реализации красит сборку, а не отдаёт `undefined`.
- Юнит: у каждого свойства новых DTO есть `description`, у каждого ответа —
  `schema` и непустой `description` (действующие гейты подхватят автоматически,
  проверить, что подхватили).
- Новые GET-ручки с query добавить в `RESEARCH_QUERY_ROUTES` — мета-гейт
  покраснеет, если забыть.
- E2E-инвариант: у опубликованного вердикта есть три причины и хотя бы одна
  локаль. Проверяется на паре ручек, а не на одной: листинг и страница по
  отдельности были зелёными ровно тогда, когда листинг показывал то, чего
  страница не открывает.

**Приёмка.** `make test-unit`, `make test-api`, `make typecheck`,
`make api-docs-check` — все зелёные. Каждый новый гейт проверен на красноту:
временно сломать источник, убедиться, что упал именно он.

## Порядок и откат

C1 → C2 → C3 → C4 → C5 → C6 → C7.

C2 не зависит от C1 по коду и может идти параллельно, но порядок линейный
специально: чистые функции проще писать, когда имена enum'ов уже зафиксированы
схемой.

Откат любого шага — отдельный коммит. Необратим только C1: миграция снимается
новой миграцией, `prisma migrate reset` на проде запрещён.

## Чего в этом ТЗ нет намеренно

Автоматического перевода (работа сайта), крона и сбора чисел из внешних
