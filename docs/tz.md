## Что уже построено и не меняется

Вселенная — один неизменяемый снимок фактов. Рабочий состав получается
композицией двух независимых обратимых фильтров:

```text
snapshot → [screen?] → [alpha?]
```

- `screen` — абсолютный отсев шлака по правилам профиля;
- `alpha` — top-N внутри перенасыщенных групп сравнения;
- включить можно оба, один или ни одного;
- без фильтров рабочий состав равен всей вселенной;
- порядок HTTP-вызовов не задаёт порядок вычисления;
- `POST` меняет состояние своего фильтра, `GET` только читает композицию;
- `enabled: false` выключает названный фильтр и не стирает его конфигурацию.

Пути и смысл сохраняют: `POST /universe/refresh`, `POST /universe/prices`,
`POST /universe/screen`, `POST /universe/alpha`, `POST /universe/compare`,
`GET /universe`, `GET /universe/status`, `GET /universe/funnel`,
`GET /universe/coverage`, `GET /config/profiles`, `GET /config/thresholds`.

Состав active selection всегда берётся одним способом:

```ts
view.candidates.filter((candidate) => candidate.passed)
```

Ни оценка, ни агенты, ни рейтинг не имеют права включать фильтры, менять
`ActiveFilterState` или отсеивать вселенную скрытым условием.

Достигнутое на шагах 06–06.1 и не подлежащее ухудшению: вселенная 2026-08-26 из
1300 монет, `deep-value` оставляет 331, пробел групп сравнения 9.97% при гейте
11% по числу и 3% по капитализации, сравнимых 47, ниш с настоящим сравнением 10
из 45.

## Что чинится этим ТЗ

Восемь конкретных вещей, каждая дальше раскрыта в своём шаге.

1. **Кодовые «агенты» обрабатывают один токен за вызов.** Оценить 331 токен —
   993 нажатия в Swagger. Заменяется одним массовым POST.
2. **Календарь разлоков вводится руками.** Главное число системы (NHY) стоит
   331 ручной записи и потому не существует. Заменяется автоматическим
   источником с честным фолбэком.
3. **Два слоя данных на одну вселенную.** `POST /snapshot/refresh` повторно
   тянет рынок и выручку после `POST /universe/prices`, создаёт второй
   `SnapshotRow` и ставит `asOfFees` равным времени запроса — прямое нарушение
   инварианта «`asOf` — время источника». Публичный `/snapshot` удаляется.
4. **Мёртвые эндпоинты врут.** `GET /config/universe` и `GET /config/sectors`
   отдают статический список из 13 токенов рядом с настоящей вселенной на 1300.
5. **Прогресс живёт в трёх местах.** `JobService` знает имя задачи,
   `UniverseService` ведёт своё состояние; идущая задача снапшота видна как
   `idle`. Заменяется одним `GET /status`.
6. **Списки приходят голым массивом.** Ни `universeVersion`, ни `builtAt`, ни
   `activeFilters`, ни `total` — происхождение приходится добирать вторым
   запросом. Вводится общий конверт ответа.
7. **Ошибка — тупик.** Три места отвечают 409 без указания, что нажать дальше.
   Вводится общий формат ошибки с `nextAction`.
8. **Нет ответа на главный вопрос.** «Почему тут нет AAVE» сейчас собирается из
   funnel, rejected, coverage и dataGaps руками. Вводится
   `GET /universe/{token}`.

## Пять слоёв и одно правило

| Слой | Что делает | Сеть | Ритм | HTTP |
|---|---|---|---|---|
| **Состав** | кто вообще во вселенной | ~25 запросов | раз в месяц | 202 + задача |
| **Числа** | цены, выручка, TVL, разлоки | ~10 запросов | по требованию | 202 + задача |
| **Отбор** | screen и alpha | нет | мгновенно | 200 сразу |
| **Оценка** | valuation, tokenomics, sectorPosition | **нет** | секунды | 200 сразу |
| **Выводы** | mechanism, critic, ranking | LLM | минуты, деньги | 202 + задача |

Правило одно: **ходит в сеть или тратит деньги — 202 и задача; считает локально
— 200 сразу.** Из него следует всё остальное. Оценка не ходит в сеть, поэтому
она дёшева, воспроизводима и может быть пересчитана автоматически кем угодно
ниже по конвейеру. Ради этого разлоки собираются отдельным эндпоинтом слоя
чисел, а не внутри оценки.

Граница фактов и мнения проходит между «Числа» и «Отбор». Всё выше неё — то,
что есть в источниках. Всё ниже — ваш вопрос к этим данным.

## Главное изменение: три кодовые оценки вместо трёх агентов

`screener`, `unlocks` и `sector-position` не агенты. Это три компонента одной
кодовой оценки, считающейся сразу по всей текущей выборке.

| Компонент | Что сохраняется | Откуда данные |
|---|---|---|
| `valuation` | дешевизна, P/Rev, take rate, абсолютные проверки | готовые поля кандидата |
| `tokenomics` | разлоки, разводнение, NHY, давление на объём | поля кандидата после `POST /universe/tokenomics` |
| `sectorPosition` | место, перцентили, peers, роль в нише | общий код сравнения, тот же, что у alpha |

Результаты, баллы, `verdict`, `missing`, источники и объяснения сохраняются
целиком. Меняется архитектурная роль: это не агенты и не per-token процессы.

Настоящими агентами остаются два LLM-модуля:

- `mechanism` — классифицирует механизм возврата ценности по документам;
- `critic` — пытается опровергнуть уже собранный тезис.

Итоговый конвейер:

```text
snapshot → [screen?] → [alpha?] → evaluation → mechanism → critic → ranking
```

Квадратные скобки — необязательный фильтр. Оценка и рейтинг обязаны работать при
любой из четырёх комбинаций, включая оба выключенных фильтра.

## Термины и контракты

### Кодовая оценка

```ts
export type EvaluationComponentName = 'valuation' | 'tokenomics' | 'sectorPosition';

export interface EvaluationBlock {
  component: EvaluationComponentName;
  title: string;
  verdict: Record<string, unknown>;
  score: number | null;
  scoreRaw?: number;
  metrics: Record<string, Metric>;
  dataQuality: number;
  missing: string[];
  notes: string;
  validator?: { dropped: string[]; stale: string[] };
  error?: string;
}

export interface CandidateEvaluation {
  coingeckoId: string;
  ticker: string;
  name: string;
  comparisonGroup: string | null;
  /** Тир данных: yield/economics/pool. НЕ тир рейтинга. */
  dataTier: Tier;
  valuation: EvaluationBlock;
  tokenomics: EvaluationBlock;
  sectorPosition: EvaluationBlock;
}

export interface EvaluationRun {
  runId: string;
  createdAt: string;
  universeVersion: string;
  builtAt: string;
  activeFilters: ActiveFilterState;
  evaluationProfileId: string;
  /** Покомпонентные хеши входа: см. «Совместимость». */
  inputHashes: {
    /** universeVersion + версия рыночных и выручных фактов + профиль. */
    perToken: string;
    /** perToken + состав группы сравнения. */
    comparative: string;
  };
  inputCount: number;
  evaluatedCount: number;
  dataGapCount: number;
  summaries: Record<EvaluationComponentName, EvaluationSummary>;
  candidates: CandidateEvaluation[];
}
```

### Совместимость считается покомпонентно

Один хеш на весь прогон делает любую подвижку фильтра поводом пересчитать всё и
объявить рейтинг несовместимым. Это неверно по существу:

- `valuation` и `tokenomics` — чистые функции одного токена. Кто ещё в выборке,
  на них не влияет. Их валидность определяет `inputHashes.perToken`.
- `sectorPosition` зависит от состава группы сравнения. Его валидность
  определяет `inputHashes.comparative`.

Отсюда поведение: сменили фильтр — `perToken` совпадает, `comparative` нет,
`sectorPosition` пересчитывается локально за секунды, остальное берётся как
есть. Ответ прямо сообщает, что переиспользовано, а что пересчитано. Никаких
409 из-за подвинутого порога.

### Профиль

`AnalysisProfile.agents` разделяется явно:

```ts
codeEvaluations: ['valuation', 'tokenomics', 'sectorPosition'];
llmAgents: ['mechanism', 'critic'];
weights: {
  tokenomics: 0.35,      // NHY: доход держателя минус разводнение
  mechanism: 0.25,       // механизм возврата ценности и качество роста
  valuation: 0.20,       // дешевизна относительно собственной выручки
  sectorPosition: 0.20,  // положение среди прямых конкурентов
};
```

`critic` в веса не входит: он штрафной множитель к итогу, а не слагаемое.
Усреднять критику с остальным — значит её разбавлять. Таблицы очков
LLM-категорий заморожены в коде и в профиль не выносятся: иначе подбором
профиля достижим любой заранее желаемый вывод.

Ключи весов совпадают с `EvaluationComponentName` и именами агентов
посимвольно. Старые `screener`, `unlocks`, `sectorPosition` против
`sector-position` — источник тихо выпадающего модуля; переименование делается
одной утверждённой миграцией на шаге 10.

## Соглашения API: одинаковые для всех эндпоинтов

Swagger сегодня — временный клиент. Всё, что здесь описано, существует ради
того, чтобы фронтенд сайта не пришлось строить на догадках, а вкладку Swagger не
приходилось перезагружать.

### 1. Конверт ответа

Любой эндпоинт, возвращающий список, отдаёт:

```jsonc
{
  "context": {
    "universeVersion": "2026-08-26",
    "builtAt": "2026-08-26T06:00:00.000Z",
    "activeFilters": { "screen": {}, "alpha": {} },
    "asOf": "2026-08-27T09:12:00.000Z"
  },
  "pagination": { "offset": 0, "limit": 50, "total": 331, "hasMore": true },
  "items": []
}
```

Без `context` число в списке не отличить ни от другого отбора, ни от другого
снимка, и полчаса уходит на поиск несуществующего бага.

### 2. Пагинация и вес

`limit` по умолчанию 50, максимум 200. Любой эндпоинт с тяжёлыми вложенными
структурами (`evaluation`, `ranking`) поддерживает `view=summary|full`, по
умолчанию `summary`. Ответ по умолчанию проверяется командой
`curl -w '%{size_download}'` и не превышает 300 КБ: мегабайты JSON вешают
вкладку, а не сервер.

### 3. Формат ошибки

Все 4xx и 5xx отвечают одинаково:

```jsonc
{
  "code": "evaluation_missing",
  "message": "Кодовой оценки для текущей выборки нет.",
  "details": { "expected": "2026-08-26", "actual": null },
  "nextAction": { "method": "POST", "path": "/evaluation/run", "body": {} }
}
```

`code` — машиночитаемый, стабильный, английский. `message` — русский, для
человека. `nextAction` обязателен везде, где действие пользователя очевидно
коду. Ошибка без `nextAction` — тупик, а тупик это дефект интерфейса.

Где сравниваются несколько условий, `details` называет расхождение поимённо.
«Несовместимо» без указания, что именно разошлось, заставляет перезапускать
вслепую.

### 4. Фоновые задачи

Долгий POST отвечает `202` и телом:

```jsonc
{ "jobId": "job_2026-08-27T09:12:00Z_universe-refresh",
  "operation": "universe/refresh",
  "statusUrl": "/status",
  "message": "Пересборка запущена: около 25 запросов и 3–5 минут" }
```

Слот один на процесс (`JobService`). Занят — `409` с `code: "job_busy"`, именем
текущей операции, её прогрессом и `nextAction` на `GET /status`.

### 5. Значения и метки

Значения enum — английские, стабильные, по ним ветвится код и фронтенд:
`low`, `medium`, `high`, `unknown`, `leader`, `challenger`, `overvalued`,
`outsider`. Русский текст едет отдельным полем рядом: `dilutionRisk` и
`dilutionRiskLabel`, `role` и `roleLabel`. Смешивать язык интерфейса со
значением поля нельзя — перевод не должен ломать сравнение.

### 6. Идентификаторы

Стабильный идентификатор сущности — `coingeckoId`. Тикер — отображение и вход
пользователя, но не ключ: один символ у двух активов это mapping failure, а не
повод выбрать строку покрупнее. Пути принимают тикер и резолвят его в
`coingeckoId`; неоднозначный тикер отвечает `409` со списком кандидатов.

### 7. Числа

Проценты — в процентах (`5.2`, не `0.052`), деньги — в USD, `null` — неизвестно
и никогда не ноль. Числа приходят числами, не строками. Каждое число
сопровождается `sourceUrl` и `asOf` источника или обнуляется валидатором.

### 8. Порядок в Swagger

Теги в порядке конвейера: `system`, `universe`, `selection`, `evaluation`,
`analysis`, `ranking`, `manual`, `config`. Основные операции в `summary`
нумерованы («ШАГ 1…»), продвинутые помечены `[advanced]`. Это единственная
навигация, которая у пользователя сейчас есть.

## Правки замороженных контрактов

**1. `UniverseCandidate` получает поля tokenomics** (шаг 09). Разлоки — такой же
факт со ссылкой и датой, как выручка, и живут там же, где она:

```ts
  /** Навес: считается из снимка, известен почти у всех, календаря не требует. */
  overhangPct: number | null;
  unlockEventsCount: number | null;
  unlockTokens30d: number | null;
  unlockTokens90d: number | null;
  unlockTokens365d: number | null;
  unlock30dPct: number | null;
  unlock90dPct: number | null;
  unlock12mPct: number | null;
  netHolderYieldPct: number | null;
  nextUnlockAt: string | null;
  nextUnlockUsd: number | null;
  nextUnlockCostInDailyVolumes: number | null;
  /** Доля эмиссии без расписания: выше 5% число не принимается. */
  tokenomicsTbdPct: number | null;
  tokenomicsState: TokenomicsDataState;
  tokenomicsSource: string | null;
  asOfTokenomics: string | null;
  // Набор объявлен один раз, в TokenomicsFields (src/core/tokenomics), и
  // подмешивается через extends: два списка одних и тех же полей разъезжаются.
```

**2. `NumericField` расширяется** полями `overhangPct`, `unlock12mPct` и
`netHolderYieldPct`. Это делает их доступными в `screen` и `alpha.rankBy`.
**Встроенные профили при этом не меняются:** порог вроде
`netHolderYieldPct >= 0` в `screen` отсекает токены до alpha и меняет секторные
рейтинги — это сознательное решение, а не побочный эффект шага.

Ранжировать по одному навесу нельзя: токен с навесом 100% и последним разлоком в
2031 году безопаснее токена с навесом 30% и клиффом через месяц.

**3. `WEIGHTS` и `AnalysisProfile.agents`** мигрируют на новые имена (см.
«Профиль»). `GET /config/thresholds` продолжает работать и отдаёт значения
профиля по умолчанию с новыми ключами; e2e-тест обновляется тем же коммитом.

**4. `SnapshotRow` и `AgentContext` перестраиваются** (шаг 11). Контекст
собирается из `UniverseView` и `EvaluationRun`, а не из второго снапшота.
`SnapshotService` и его контроллер удаляются целиком, вместе с `asOfFees`,
равным времени запроса.

**5. `AGENT_NAMES`** сокращается до `['mechanism', 'critic']`; `BaseAgent`
переименовывается в `BaseLlmAgent`.

**6. `Tier` разводится на два типа**: `DataTier` (`yield`, `economics`, `pool`,
`rejected`) и `RankTier` (`A`, `B`, `C`, `watchlist`). Одно слово на два разных
смысла в одном ответе — гарантированная путаница в отчёте и на сайте.

# ШАГ 08 — Источник разлоков: проверка и решение

**Цель.** Доказать фактическими запросами, откуда автоматически брать календарь
будущей эмиссии для всей рабочей выборки, и принять решение о фолбэке. Кода в
`src/` этот шаг не создаёт.

Старое предположение о бесплатном `https://api.llama.fi/emissions` мертво:
endpoint отвечает `402`, официальный Token Unlocks живёт на
`https://pro-api.llama.fi/api/emissions`.

### Кандидаты

1. **Mobula** `metadata` / `multi-metadata`: в документации заявлены
   `release_schedule` и bulk-запрос. Главный кандидат на бесплатный источник,
   фактическое покрытие нашей выборки не измерено.
2. **DeFiLlama Pro** emissions — опциональный, при наличии ключа.
3. **CryptoRank · Messari · Tokenomist** — только как дополнительные адаптеры
   после реальной проверки ответа, условий доступа и лицензии.
4. **CoinGecko** `circulating_supply` / `total_supply` — текущий навес и
   прошлая фактическая эмиссия. Подменять этим будущий календарь 30/90/365
   запрещено.

### Одноразовый spike

`scripts/check-tokenomics-sources.ts`, удаляется тем же коммитом, которым
проверенный парсер переезжает в `src/core/tokenomics/`. Скрипт:

- делает реальные запросы и сохраняет сырые ответы через `StoreService.saveRaw`
  до всякой обработки;
- показывает фактическую схему каждого ответа;
- берёт не меньше 20 активов текущей active selection, включая HYPE, AAVE,
  ARB/OP или их фактические аналоги в выборке;
- считает покрытие по числу токенов **и по капитализации**;
- отдельно считает exact match, `mapping_failed`, `source_missing`, `stale`;
- склеивает по устойчивому идентификатору или контракту, а не по тикеру;
- проверяет bulk-размер, rate limit, дату источника и открываемость
  `sourceUrl`;
- различает `401`, `402`, `429` и сетевую ошибку.

### Результат прогона 2026-08-27

Проверены запросами четыре источника. Принят один.

**DeFiLlama emissions, публичные датасеты, без ключа.** Список слагов на
`https://defillama-datasets.llama.fi/emissionsProtocolsList`, документ протокола
на `.../emissions/{slug}`. Идентификатор токена лежит внутри документа
(`gecko_id`), поэтому карта `coingeckoId → slug` строится обходом всех 370
документов: 467 МБ, 15 секунд, ноль сбоев. `asOf` — заголовок `last-modified`.
Склейка точная, `mapping_failed` ноль на 316 токенов.

**Mobula отклонена.** `release_schedule` существует (проверено на Uniswap,
Arbitrum, Celestia), но: даты источника нет ни в теле, ни в заголовках — метрика
без `asOf` обнуляется валидатором; `multi-metadata` урезает ответ и календарь из
него выбрасывает, значит только одиночные запросы по 2 секунды; из выборки в 40
календарь нашёлся у четырёх, все уже покрыты DeFiLlama; TIA разошёлся с
DeFiLlama на четверть (8.06% против 10.91%). Имя не идентификатор: запрос
`asset=Aave` возвращает AUSDT.

**DeFiLlama Pro** не проверялся: ключа нет, бесплатный путь закрыл задачу.
**CoinGecko** даёт `circulating` и `totalSupply` — это навес, не календарь.

### Покрытие и что из него следует

| Метрика | По числу | По капитализации |
|---|---|---|
| `overhangPct` | 99.37% | 99.77% |
| `unlock12mPct` | 10.44% | 34.41% |

Календарь по сценарию B, но базовая метрика покрывает почти всё. Отсюда главное
решение шага: **метрика навеса становится базой, календарь — уточнением**.

### Годовая эмиссия снята как метрика

Ни один источник её не содержит. И она не нужна: вестинг неоднороден, среднее по
трём годам прячет клифф. Держателю важен ближайший год, а не среднее.

### Пробел в расписании дисквалифицирует число

49% документов DeFiLlama (205 из 421) имеют больше 1% эмиссии без графика:
поле `supplyMetrics.tbdAmount`. У Hyperliquid без графика 61% эмиссии, у Jupiter
50%, у Aster 42%. Разводнение по такому расписанию — не число с погрешностью, а
отказ: порог **`tbdAmount > 5%` от `maxSupply` → `matched_unparsed`**.

### Знаменатель полноты — `maxSupply`, не `adjustedSupply`

`adjustedSupply` это эмиссия, у которой график есть. Деление на неё завышало
ровно на долю пробела: 100% клиффов EDGE при 35% пробела давали 154%. После
правки ни один документ из 421 не даёт клиффов выше 105%.

### Схема события DeFiLlama

```jsonc
{ "timestamp": 1659657600,
  "cliffAllocations": [
    { "recipient": "Funds 1", "category": "community",
      "unlockType": "cliff", "amount": 120000000 }],
  "linearAllocations": [
    { "recipient": "App Rewards (forecast)", "category": "Uncategorized",
      "unlockType": "linear_start", "previousRatePerWeek": 0,
      "newRatePerWeek": 109800000, "endTimestamp": 1863129600 }],
  "summary": { "totalTokensCliff": 121000000 } }
```

Клифф несёт количество, линейная аллокация — **ставку в неделю**. Складывать их
как однородные события нельзя: четырёхлетний вестинг посчитается одним днём.
Линейный поток интегрируется по сегментам, следующая смена ставки у того же
получателя обрывает предыдущую. Пары `linear_end` в данных нет.

`(forecast)` в имени получателя — прогноз наград, то есть эмиссия, а не вестинг.
Встречается у 6 документов из 421; помечается флагом, отдельной метрикой не
считается.

Сумма клиффов сверяется с `summary.totalTokensCliff`; расхождение больше 0.5% —
отказ по токену, а не выбор своей цифры.

### Устаревание определяется данными, не датой файла

`last-modified` — время перегенерации датасета. Календарь, который месяц никто
не правил, выглядит просроченным именно потому, что он верен. Признак
отставшего адаптера: **впереди событий нет И расписание покрыло меньше 99%
эмиссии И `floatPct` ниже 90%**. Порог по дате файла для этого не годится.

### Решение принимается здесь, а не по ходу шага 09

`tokenomics` имеет наибольший вес в композите (0.35). Если источник покроет
мало, компонент вернёт `null` у большинства токенов, веса перенормируются, и
рейтинг тихо станет продуктом из двух компонентов вместо четырёх. Поэтому порог
фиксируется до реализации:

- **покрытие ≥ 60% по капитализации active selection** → Mobula (или
  победивший источник) становится основным, шаг 09 пишется по нему;
- **покрытие 20–60%** → источник основной, а недостающее закрывается вторым
  автоматическим адаптером, а не человеком: ручное заполнение сотен токенов —
  тот же тупик, из которого этот эпик выводит. `GET /universe/data-gaps`
  остаётся очередью задач для адаптеров, а не рабочим местом оператора;
- **покрытие < 20%** → автоматический источник не принимается, шаг 09 сводится
  к ручному слою плюс `floatPct`/`fdvToMcap` как единственным измеренным
  признакам навеса. Вес `tokenomics` в этом случае пересматривается явной
  правкой профиля, а не молчаливой перенормировкой.

**Приёмка выполнена 2026-08-27.** Схема основного источника показана · покрытие
измерено по числу и по капитализации · cliff и linear показаны обе · `401`,
`402`, `429` и сетевой сбой различимы · склейка по `coingeckoId`, тикер в ней не
участвует · у каждого принятого числа есть `sourceUrl` и `asOf` · сработал
сценарий B, с поправкой: недостающее закрывает навес, а не человек.

**Запрещено.** Писать production-парсер по документации без реального ответа.
Считать `totalSupply − circulating` разводнением следующих 12 месяцев. Начинать
шаг 09 до принятого решения о фолбэке.

**СТОП.**

# ШАГ 09 — `POST /universe/tokenomics`: разлоки как факт

**Цель.** Календарь будущей эмиссии и производные от него числа лежат в
кандидате вселенной рядом с выручкой — со ссылкой, датой источника и способом
склейки.

### Почему это слой фактов, а не часть оценки

Разлок — такое же внешнее число, как выручка. Положив его в оценку, мы бы
получили оценку, которая ходит в сеть: занимает слот задачи, требует 202 и
polling, и не может быть автоматически пересчитана рейтингом. Положив его в
кандидата, мы оставляем оценку чистой функцией. Это и есть причина всей
остальной лёгкости ниже по конвейеру.

### Контракт

```ts
export type TokenomicsDataState =
  | 'available'
  | 'known_zero'
  | 'mapping_failed'
  | 'source_missing'
  | 'source_stale'
  | 'source_error'
  /** Документ найден, но число из него не берётся: пробел в расписании,
   *  нераспознанная сумма или расхождение с итогом источника. */
  | 'matched_unparsed';

export interface UnlockEvent {
  date: string;
  tokens: number;
  category: 'team' | 'investors' | 'community' | 'ecosystem' | 'other' | 'unknown';
  origin: 'provider' | 'manual';
  sourceUrl: string;
  asOf: string;
}

/**
 * Линейный поток. Добавлен на шаге 09: источник даёт ставку в неделю до
 * endTimestamp, а не количество, и втиснутый в UnlockEvent он либо
 * складывается с клиффом как однородное событие, либо разворачивается в
 * придуманные даты. Ставка ноль — терминатор потока, а не пустое событие.
 */
export interface UnlockStream {
  recipient: string;
  category: UnlockEvent['category'];
  startsAt: string;
  endsAt: string;
  tokensPerWeek: number;
  origin: 'provider' | 'manual';
  sourceUrl: string;
  asOf: string;
}

export interface TokenomicsFacts {
  coingeckoId: string;
  ticker: string;
  provider: string | null;
  providerId: string | null;
  matchedBy: 'coingecko_id' | 'contract' | 'provider_id' | 'symbol' | 'none';
  state: TokenomicsDataState;
  /** Только будущие клиффы: прошлое уже сидит в circulating. */
  events: UnlockEvent[];
  /** Потоки получателя группой, включая уже истёкшие терминаторы. */
  streams: UnlockStream[];
  /** Доля эмиссии без расписания. Выше 5% — число не принимается. */
  tbdPct: number | null;
  /** Расписание покрывает столько процентов maxSupply. */
  schedulePct: number | null;
  /** Поток помечен источником как прогноз: это эмиссия, а не вестинг. */
  includesForecast: boolean;
  sourceUrl: string | null;
  asOf: string | null;
  note: string;
}
```

**Пустой массив событий не становится `known_zero`.** Ноль допустим, только
если источник явно отдал полный календарь и отсутствие будущей эмиссии. Иначе
`source_missing`: «источник нас не знает» и «эмиссии не будет» — это разные
утверждения, и второе стоит денег.

### Поведение эндпоинта

- работает по всей группе, параметра `{token}` нет;
- карта `coingeckoId → slug` строится обходом 370 документов и **живёт отдельным
  кэшем со сроком жизни вселенной**: она меняется с составом, то есть раз в
  месяц. Ежедневный прогон тянет только документы совпавших слагов, иначе
  467 МБ качаются на каждое обновление чисел;
- сырой ответ ложится на диск до обработки;
- фоновая задача: `202`, слот `JobService`, прогресс в `GET /status`;
- суточный кэш; `force=true` обходит его;
- пустой ответ не кэшируется — неудачный ответ в суточном кэше живёт сутки и
  притворяется фактом;
- состав вселенной, `version` и `builtAt` не меняются, меняются только числа.

### Что считает код после загрузки

Всё через `money.ts`, ошибка float переворачивает знак NHY на пограничном
активе.

**Базовая метрика — навес.** Не зависит от чужих адаптеров, известна у 99.4%
выборки, считается из снимка вселенной без единого запроса:

```text
overhangPct = (totalSupply − circulating) / circulating × 100
```

`totalSupply` ниже `circulating` — рассогласование источника, а не отрицательный
навес: результат `null`, не ноль. Навес говорит **сколько** может выйти, но не
когда: токен с навесом 5% безопасен и без календаря, с навесом 100% опасен даже
без него.

**Уточнение — календарь.** Считается там, где расписание принято:

```text
unlock12mPct      = unlockTokens365d / circulating × 100
unlock30dPct      = unlockTokens30d  / circulating × 100
unlock90dPct      = unlockTokens90d  / circulating × 100
netHolderYieldPct = holderYieldPct − unlock12mPct
nextUnlockCostInDailyVolumes = nextUnlockUsd / vol24hUsd
```

Числитель приходит от DeFiLlama, знаменатель — от CoinGecko, и это **разные
учёты**: у WhiteBIT расписание закрыто на 100%, а в обращении 40% — биржа держит
свои токены разлоченными, но вне рынка. Обратный случай измерен на CC: навес
ноль при календаре на +20% за год. Оба числа остаются, расхождение называется в
`notes` и в warnings прогона, сверять их между собой нельзя.

`nextUnlockCostInDailyVolumes` обязателен: разлок на 3 дневных объёма и на 30 —
принципиально разные события. Считается он только от клиффа: у линейного
вестинга дискретного момента нет, и «ближайший разлок» для него — выдумка.
Измерено: клифф впереди у 12 из 28 строк с календарём, доля видна в warnings.
`netHolderYieldPct` считается, только когда известны обе половины; одна известна
— поле `null` плюс запись, какая именно половина отсутствует и куда смещён результат.

**Пустой календарь не даёт ноль сам по себе.** `known_zero` только когда
расписание покрыло не меньше 99% эмиссии либо `floatPct` не ниже 90%. Иначе
`matched_unparsed` или `source_stale`.

**`realizedEmission` — в TODO, вне MVP.** Фактический выпуск между двумя нашими
снимками закроет тех, у кого календаря нет и не будет: XMR, KAS, биржевые
токены. Ноль внешних запросов, работает со второго снимка.

### Необязательный ручной слой

Возвращается — но никогда не как условие прохождения оценки:

- `POST /manual/unlocks` — `{ ticker, date, tokens, category, sourceUrl, asOf }`,
  **`sourceUrl` и `asOf` обязательны**; `GET /manual/unlocks/{token}`;
  `DELETE /manual/unlocks/{id}`. `asOf` — дата документа-источника: без неё
  метрика обнуляется валидатором, а время записи вместо неё было бы подделкой
  происхождения. Тикер разрешается в `coingeckoId` по снимку, неоднозначный — 409.
- `POST /manual/overrides/{token}` перенесён на **шаг 13**: его четыре поля
  никто не читает до `incentiveAdjustedRevenue`, а эндпоинт, принимающий числа
  без потребителя, — заглушка будущего шага.

Главный из оверрайдов — `incentives12mUsd`, стоимость раздаваемых токенов. Её
нет ни в CoinGecko, ни в сводках DeFiLlama, а без неё «выручка 8 млн» и
«выручка 8 млн при 12 млн стимулов» выглядят одинаково.

Правило конфликта: ручное значение и значение API одной семантики, расходящиеся
более чем вдвое, попадают в `notes`, и берётся значение API. Тихо предпочесть
ручной ввод нельзя. Происхождение каждого события видно в `origin`.

**Приёмка выполнена 2026-08-28.** Один POST собирает разлоки по всей вселенной ·
сырые ответы на диске · `unlock12mPct` и `netHolderYieldPct` заполнены у
покрытых · у каждого числа `sourceUrl` и `asOf` источника · непокрытый токен
получает типизированное состояние, а не ноль · `POST /manual/unlocks` без
`sourceUrl` → 400 · ручная запись видна как `origin: 'manual'` · повтор в
течение суток не ходит в сеть · состав и `builtAt` не изменились.

**Измерено на вселенной 2026-08-26 (1300 монет):** карта из 370 документов за
55 с без ошибок, документы 220 совпавших слагов за 30 с, календарь принят у
8.77% строк и 77.96% капитализации, навес — у 98%. Знаменатель здесь полная
вселенная, у шага 08 — active selection: числа несравнимы напрямую.

**Принятые расхождения с этим ТЗ:** `streams` добавлены в контракт; `asOf`
обязателен в ручном вводе; `/manual/overrides` перенесён на шаг 13. Склейка по
контракту отложена: она требует bulk-метода `platforms` в `CoingeckoService`, а
измеренный `mapping_failed` без неё равен нулю. Возврат к ней потребует
`force=true`, поскольку карта строится один раз на версию вселенной.

**Запрещено.** Подставлять ноль вместо неизвестного календаря. Считать
`totalSupply − circulating` разводнением 12 месяцев. Складывать vesting-события
с дневной эмиссией, не доказав, что это разные потоки. Делать ручной ввод
обязательным.

# ШАГ 10 — `POST /evaluation/run`: единая массовая оценка

**Цель.** Один вызов оценивает всю текущую выборку и возвращает по каждому
токену `valuation`, `tokenomics` и `sectorPosition`. Сети — ноль.

### Вход

Всегда текущий `UniverseView`, строки с `passed: true`:

- оба фильтра включены → survivors `screen → alpha`;
- только screen → survivors screen;
- только alpha → survivors alpha по полному снимку;
- оба выключены → вся вселенная.

Список тикеров в запросе не принимается. Фильтры сам не включает.

```ts
export class EvaluationRunDto {
  /** Профиль шкал и порогов оценки. Отбор он не меняет. */
  profileId?: string;
  /** Пересчитать, игнорируя совместимый прогон. */
  refresh?: boolean;
}
```

Отвечает `200` синхронно: расчёт локальный. Слот задачи не занимает. На 1300
кандидатах укладывается в единицы секунд — иначе это дефект реализации, а не
повод возвращать 202.

### `valuation`

Только готовые поля кандидата. Ни сетевых запросов, ни повторного расчёта
метрик вселенной.

Проверки против `profile.thresholds`: известна `revenue12mUsd`, выручка не ниже
`minAnnualRevenueUsd`, капитализация не ниже `minMcapUsd`, `pRev` не выше
`maxPRev`. Результат — `verdict.passed` и `failedChecks` с причинами на
русском.

**Проверки не меняют universe.** И у каждой в ответе указано, кем она уже была
применена:

```jsonc
"checks": [
  { "id": "mcapAboveMin", "passed": true, "appliedBy": "screen" },
  { "id": "pRevSane",     "passed": false, "appliedBy": "evaluation",
    "reason": "P/Rev 84 при пороге 60" }
]
```

Без `appliedBy` поле бессмысленно: при включённом `deep-value` все проверки
тривиально пройдены, потому что screen применил те же пороги, а при выключенном
screen то же поле работает скрытым третьим фильтром. Пользователь должен видеть
разницу, а не гадать.

Балл: `100 − 100 × pRev / maxPRev`, зажать в 0..100. Нет выручки или P/Rev →
`score: null`, не ноль: отсутствие данных и дорогая оценка — разные вещи.

В `verdict` обязателен `takeRatePct` с пояснением: протокол, собирающий 500 млн
комиссий и оставляющий себе 2%, — это бизнес поставщиков капитала, а не токена.

Метрики через `metric()`: `mcapUsd`, `fdvUsd`, `revenue12mUsd`, `fees12mUsd`,
`pRev`, `fdvRev`, `takeRatePct`, `tvlUsd`. Все проходят `ValidateService`.

### `tokenomics`

Читает поля кандидата, заполненные шагом 09, и объясняет их. В сеть не ходит.

Балл: `NHY ≥ 5%` → 90..100; `0..5%` → `50 + NHY × 8`; `NHY < 0` →
`50 + NHY × 2.5`, не ниже 0.

`verdict.dilutionRisk`: `low` < 5%, `medium` 5–15%, `high` > 15%, `unknown` —
плюс `dilutionRiskLabel` на русском. `hardFilterFail = true` при
**подтверждённом** отрицательном NHY: неизвестный календарь хард-фильтром не
является.

Неполные данные:

- календарь неизвестен → NHY не выдаётся как подтверждённое число, в `notes`
  «разводнение неизвестно, NHY завышен»;
- holder revenue неизвестна → «возврат ценности неизвестен, NHY занижен»;
- подтверждённый ноль holder revenue остаётся нулём;
- обе части неизвестны → `score: null`;
- отсутствие календаря не заменяется оценкой по FDV или market cap.

В `verdict` также `floatPct` и `fdvToMcap`: низкий float — то же разводнение,
только ещё не оформленное календарём.

### `sectorPosition`

Расчёт перцентилей выносится из `applyAlpha` в чистую функцию, которую
используют **и** alpha, **и** оценка. Две независимые реализации одной формулы
запрещены — они разъедутся за шаг и разъедутся тихо.

Alpha включена — переиспользуется уже посчитанный `AlphaView`. Alpha выключена —
те же перцентили считаются по входу оценки, но никого не отсекают и не меняют
`ActiveFilterState`. Компонент, исчезающий при законной комбинации фильтров, —
дефект.

Результат: `sectorScore`, `rankInSector`, `revenueSharePct`, перцентиль каждой
метрики, `peers`, `comparisonAvailable`, `selectionApplied`.

Роль: `leader` — доля выручки ≥ 40% и перцентиль эффективности ≥ 60;
`overvalued` — перцентиль дешевизны < 30 и перцентиль доли < 50; `challenger` —
перцентиль эффективности ≥ 50; `outsider` — остальное; `unknown` — peers или
метрик не хватает. Рядом `roleLabel` на русском.

Малый сектор не получает выдуманный балл: `score: null` плюс список доступных
peers. Это не удаляет токен из выборки.

### Хранение

```text
data/evaluations/<date>/<runId>.json
data/evaluations/latest.json
```

Один воспроизводимый прогон целиком, а не тысячи per-token файлов. Ключ
переиспользования — покомпонентные хеши из раздела «Совместимость».

### HTTP

- `POST /evaluation/run` → `200`, конверт с `context`, `summaries`, `runId` и
  сводкой «переиспользовано / пересчитано».
- `GET /evaluation/latest` → конверт, пагинация, `view=summary|full`.
- `GET /evaluation/{token}` → три компонента. Токена не было в том прогоне →
  **`200` с `status: 'not_in_selection'`**, причиной и `nextAction`, а не 404:
  для продукта, где сценарий начинается с ввода тикера, 404 — худший из
  возможных ответов.

### Рефакторинг

Удалить `ScreenerAgent` и его регистрацию в `AGENT`. `UnlocksAgent` и
`SectorPositionAgent` не создавать. Переиспользовать `ValidateService` и
`metric()`. Мигрировать ключи весов.

**Приёмка.** Все четыре комбинации фильтров дают оценку ровно по
`status.passed` · один POST создаёт все три компонента · alpha выключена —
`sectorPosition` считается, состав не меняется · сетевых вызовов ноль ·
подтверждённый отрицательный NHY даёт `hardFilterFail`, неизвестный календарь —
нет · **негативный тест: метрика без источника обнуляется валидатором с
`droppedReason: 'no_source'`, `dataQuality` падает, поле уходит в `missing`** ·
`appliedBy` различает проверку screen и проверку оценки · смена только alpha
пересчитывает `sectorPosition` и переиспользует остальное · список страницами с
`context`.

**Запрещено.** Три отдельных POST. Называть компоненты агентами. Ходить в сеть.
Менять `screen`/`alpha` из оценки. Исключать строку из оценки из-за пробела в
данных. Дефолты вместо отсутствующей выручки.

- `POST /snapshot/refresh`, `GET /snapshot`, `GET /snapshot/{token}` и
  `SnapshotService` — второй слой данных поверх `POST /universe/prices`, с
  `asOfFees`, равным времени запроса. Это нарушение инварианта происхождения,

- `GET /agents` и `POST /agents/{name}/{token}` в текущем виде: заменяются на

- e2e-тесты удалённых эндпоинтов удаляются тем же коммитом.

### Готовность к сайту

Проверяется сейчас, потому что позже это переделка контракта, а не добавка:
CORS настраивается через `.env`; `GET /api/openapi.json` отдаёт спецификацию
для генерации клиента; тексты не содержат HTML и markdown-разметки (markdown
живёт только в отчётах); сортировка и фильтрация списков — через query, а не
через клиентскую обработку полной выдачи.

**Приёмка.** `GET /status` показывает идущую задачу любого типа и корректный
`nextAction` в каждом из состояний: вселенной нет · вселенная старая · оценки
нет · оценка устарела · всё свежо · `GET /universe/AAVE` объясняет присутствие,

ответах по умолчанию не превышает 300 КБ · любая ошибка 4xx содержит `code` и
`nextAction`.

**Запрещено.** Оставлять два источника одного числа. Отвечать 404 на известный
тикер. Держать состояние задачи в двух сервисах. Возвращать список без
происхождения.

# ШАГ 12 — LLM-сервис со строгой схемой

**Цель.** Единственный разрешённый путь к модели. Агентов на этом шаге нет.

`LlmService.structured<T>(prompt, schema, toolName, opts)` вызывает модель
только через tool use, затем обязательно выполняет `schema.parse()`. Модель
вернула не то — падаем сразу и понятно, а не тащим мусор дальше по конвейеру.

Системные правила (`src/core/llm/system-rules.ts`), передаются всегда:

1. Модель не вычисляет числа — арифметику делает код.
2. Модель не вспоминает проект по памяти.
3. Любое утверждение опирается на переданный текст.
4. Ссылки только из входа; нет ссылки — утверждения нет.
5. Нет данных → `missing` и `null`, а не догадка.
6. Никаких прогнозов цены, рекомендаций и целевых уровней.
7. Неуверенность выражается через `confidence`, а не осторожными формулировками.

zod v4 и встроенный `z.toJSONSchema`. **Фактический вывод проверить реальным
вызовом и показать**, а не подгонять вслепую: `zodToJsonSchema` из v3 не
подходит. Формат tool use сверить с
`https://docs.claude.com/en/docs/build-with-claude/tool-use`.

Ретраи с экспоненциальной задержкой. Клиент создаётся лениво: без ключа
приложение собирается, а при вызове отвечает понятной ошибкой с
`nextAction: mock=true`. Ключ не логируется и не попадает в `sourceUrl`.

Кэш включает `token`, имя агента, модель, `promptVersion`, `schemaVersion` и
хеш входных документов и фактов. **`activeFilters` в ключ не входит:** один и
тот же факт не оплачивается повторно из-за другой выборки — именно это делает
пять профилей почти бесплатными. Результат с `error` не кэшируется. Из кэша
объект возвращается тоже через `parse`.

`LlmMockService` с тем же интерфейсом: первое значение для enum, `null` для
чисел, `'[mock]'` для строк, `[]` для массивов, `false` для boolean. Результат
обязан проходить настоящий `schema.parse()`.

Временный `POST /debug/llm-ping` со схемой `{ ok: boolean, echo: string }`,
**удалить после проверки**.

**Приёмка.** Реальный tool use проходит zod · mock проходит ту же схему · без
ключа понятная ошибка вместо стектрейса · несовместимая схема падает на
`parse()` · ключ нигде не логируется · временный эндпоинт удалён.

**Запрещено.** Свободный текст с последующим `JSON.parse`. Пропускать
`schema.parse()`. Вызов без системных правил. Кэшировать невалидированное.

**СТОП.**

# ШАГ 13 — Документация и агент `mechanism`

**Цель.** Ответить на то, что числом не берётся: каким механизмом ценность
доходит до держателя, при каких условиях он выключается и на чём держится рост.

### Документация собирается автоматически

Ручная загрузка по каждому из сотен токенов — это тот же тупик, что и ручной
календарь разлоков. Основной путь: `POST /documents/refresh` берёт официальные
ссылки из уже загружаемых данных (`url` протокола DeFiLlama, ссылки CoinGecko
по очереди пробелов), тянет текст, сохраняет его с `sourceUrl`, `fetchedAt` и
хешем содержимого.

**Покрытие доказывается тем же способом, что и на шаге 08:** сначала прогон по
20 токенам с показом, у скольких получилось извлечь пригодный текст. Живые
сайты документации часто отдают пустую страницу без JS. Меньше половины — путь
меняется до написания production-кода, а не после.

Неофициальные статьи и поисковые сниппеты доказательством механизма не
являются. `POST /manual/docs/{token}` остаётся **необязательным** override для
случая, когда автоматически документ не достался.
`GET /universe/data-gaps` — рабочая очередь для этого.

### Схема

Все поля — категории, ни одного числового кроме `confidence`:

- `feeSwitchStatus`: `none` / `proposed` / `voted_not_active` / `active_unpaid` /
  `active_paid` / `unknown` — проголосован не равно выплачивается;
- `valueRoute`: `buyback` / `burn` / `cash_distribution` /
  `staking_from_revenue` / `staking_from_emissions` / `mixed` / `none` /
  `unknown` — стейкинг из комиссий создаёт ценность, из новой эмиссии нет;
- `buybackSource`: `revenue` / `treasury` / `none` / `unknown` — выкуп из
  выручки устойчив, из казны конечен;
- `tokenRequired`: `required` / `useful` / `governance_only` / `none` /
  `unknown`;
- `conditionsOrGates: string[]` — при каких условиях механизм выключается;
- `recurringShare`, `concentration`, `dependsOnIncentives`, `growthCharacter`;
- `evidence`: `{ claim, sourceUrl (валидный URL), documentAsOf }`;
- `missing: string[]`, `confidence: 0..1`.

### Балл считает код

Таблица заморожена в коде: feeSwitch `active_paid` 30, `voted_not_active` 12,
`proposed` 4; valueRoute `buyback`/`staking_from_revenue` 25, `treasury_only` 8,
`staking_from_emissions` 0; buyback `revenue` 15, `treasury` 5; tokenRequired
`required` 10, `useful` 5; recurring `mostly_recurring` 10, `mixed` 5;
dependsOnIncentives `no` 10, `partially` 4; growthCharacter `organic` +10,
`subsidized` 0, `likely_manipulated` −15. Сумма × `(0.5 + 0.5 × confidence)`,
зажать в 0..100.

Численная часть — тоже код: `turnoverPct` выше 50% → флаг «оборот X% от
капитализации за сутки, проверьте wash trading»; ниже 0.5% → «токен неликвиден,
выход из позиции будет дорогим». Каждый флаг −10. Известен
`incentives12mUsd` → `incentiveAdjustedRevenue = revenue12mUsd − incentives12mUsd`;
отрицательный результат → `notes` «Экономика отрицательная после стимулов».
Стимулы неизвестны → запись в `missing`, **ноль не подставлять**.

### Сверка с числами обязательна

- модель говорит `none`, а `holdersRevenue12mUsd > 0` подтверждённо → «модель
  не нашла механизм, который данные показывают»;
- модель говорит `active_paid`, а holder revenue пуст или ноль → «механизм
  заявлен, выплат в данных нет».

Расхождение пишется в `verdict.contradictions` и домножает `confidence` на 0.5.
Дешёвая проверка, ловит и плохую документацию, и выдумки модели.

`hardFilterFail = true` только при совпадении категориального провала
(feeSwitch в `none`/`unknown` И valueRoute в `none`/`staking_from_emissions`/
`unknown` И tokenRequired в `governance_only`/`none`/`unknown`) **и**
подтверждённого нуля или отсутствия holder revenue. Одного мнения модели
недостаточно.

### Без документации

`score: null`, `missing: ['нет документации для <TOKEN>']`, в `notes` — как
загрузить. Численные флаги и `holderYieldPct` отдаются: они от модели не
зависят. **Ни при каких условиях не отвечать по памяти модели.**

`POST /analysis/mechanism/{token}` остаётся для точечной отладки и помечен
`[advanced]`. В полном прогоне агент запускается оркестратором шага 15.

**Приёмка.** Показано покрытие автосбора документов на 20 токенах · без
документации — честный отказ без вызова модели, численные флаги на месте · с
документацией `evidence` непуст, **одна ссылка открыта руками и утверждение там
есть** · балл считает код · `contradictions` ловит расхождение с holder revenue
· с `mock: true` работает без ключа · другой screen/alpha не вызывает повторный
LLM при тех же документах и фактах.

**Запрещено.** Отвечать по памяти. Давать модели числа для вычислений. Числовые
поля в схеме кроме `confidence`. `evidence` без валидного URL. Выносить таблицу
очков в профиль. Делать ручную документацию обязательной.

**СТОП.**

# ШАГ 14 — Агент `critic`

**Цель.** Опровергнуть тезис, а не подтвердить. Работает по верхушке: деньги
идут туда, там и нужна проверка.

Без совместимой `CandidateEvaluation` и результата `mechanism` не запускается —
критика вслепую это генератор общих слов.

Модели передаётся выжимка, а не сырой JSON: `verdict`, `score`, `dataQuality`,
`missing` по каждому компоненту плюс уже присутствующие в них источники.

Схема: тезис одной фразой; **один** конкретный проверяемый `killerFact`, который
полностью разрушил бы тезис; `whereToCheck`; `isFalsifiable`;
`successWithoutToken`; `ifIncentivesStop`; `singleSourceRisk`;
`liquidityConcern` (`none`/`moderate`/`severe`/`unknown`); `dataGaps`;
`confidenceInThesis`.

Балл считает код: база `confidenceInThesis × 100`; штрафы `isFalsifiable: false`
−30, `successWithoutToken: true` −25, `singleSourceRisk: true` −10,
`liquidityConcern: severe` −20, `moderate` −8. Штраф за нефальсифицируемость не
придирка: тезис, который нельзя опровергнуть, нельзя и подтвердить.

Промпт требует конкретики: не «есть риски регулирования», а «если доля выручки
от одного пула упадёт ниже X, механизм выкупа остановится». Не получается
назвать конкретный факт — `isFalsifiable: false`.

`critic` в средневзвешенный композит не входит: на шаге 15 он становится
множителем.

**Приёмка.** Без prior results — честный отказ с инструкцией ·
`killerFact` конкретен и проверяем · `whereToCheck` указывает на входной
источник · общая фраза о рисках означает плохой промпт и дорабатывается ·
повтор использует кэш.

**Запрещено.** Запускать вслепую. Принимать общий текст как `killerFact`.
Позволять критику менять кодовые метрики.

**СТОП.**

# ШАГ 15 — Рейтинг

**Цель.** Один вызов превращает оценку и выводы агентов в тиры и карточки. Ни
одной обязательной подготовительной команды сверх того, что уже сделано.

### Вход

`POST /ranking/run` читает последнюю кодовую оценку. **Оценки нет или она
несовместима — рейтинг пересчитывает её сам** и сообщает об этом в ответе:
расчёт локальный, дешёвый и не требует сети, поэтому заставлять пользователя
нажать ещё одну кнопку не за что. 409 остаётся ровно один — занятый слот
задачи.

Alpha включать не обязательно. Работают все четыре комбинации фильтров.

### Защита от дорогого прогона

`POST /ranking/plan` — без сети и без LLM: сколько токенов в выборке, сколько
из них требуют вызова модели, сколько возьмётся из кэша, `estimatedCalls` и
оценка стоимости.

`POST /ranking/run` при `estimatedCalls` выше `LIMITS.maxLlmCallsWithoutConfirm`
(`src/config/limits.ts`, значение в git) требует `confirmLargeRun: true` и
возвращает `409` с точным числом и ссылкой на план. Это защита от случайного
прогона по всей вселенной при выключенных фильтрах, а не скрытое требование
включить alpha.

Порог, живущий в теле запроса или в профиле, защитой не является.

### Оркестрация

Кандидаты не исчезают ни на одном этапе:

- код-хард-фильтр → строка остаётся, LLM не вызывается, причина записана;
- нет документов → строка остаётся как data gap, LLM не вызывается;
- `mechanism` считается или берётся из кэша;
- `critic` — только после `mechanism` и только для верхушки предварительного
  композита (≥ 45).

Предварительный и финальный композит считает **одна функция**: `composite()`,
вызываемая без критика и с критиком. Две реализации одной формулы разъедутся.

Fan-out через `p-limit`, 3–4 одновременно. Входной хеш фиксируется до первого
вызова: обновление цен во время прогона не подмешивается в уже начатую работу.

Фоновая задача: `202`, прогресс в `GET /status`.

### Композит и тиры

```text
base  = weightedMean(valuation, tokenomics, sectorPosition, mechanism)
final = base × (0.6 + 0.4 × criticScore / 100)
```

Отсутствующий score не получает ноль; веса нормируются на сумму доступных
компонентов. Доступного слишком мало — `composite: null`. **В карточке видно, по
скольким компонентам и с какой суммой весов посчитан балл:** композит из одного
компонента и композит из четырёх — разные утверждения с одинаковым числом.

`rankTier` по `profile.tierCuts`: хард-фильтр → `watchlist`; `composite: null`
или `dataQuality` ниже `minDataQuality` → `C`; `composite ≥ a` и
`dataQuality ≥ 0.7` → `A`; `composite ≥ b` → `B`; иначе `C`. Внутри тира порядок
условный — это тиры, а не отсортированный список.

Хард-фильтры (`valuation.verdict.passed === false`,
`tokenomics.verdict.hardFilterFail`, `mechanism.verdict.hardFilterFail`) уводят
карточку в watchlist, но **не удаляют её**: в ней остаются причина и событие,
которое вернуло бы проект в основной рейтинг.

### Карточка

Группа сравнения и peers; капитализация; выручка и её `dataState`; комиссии;
take rate; holder revenue; P/Rev; механизм возврата ценности и
`contradictions`; NHY, float, разлоки и ближайшее событие в дневных объёмах;
качество выручки; позиция в нише и роль; критика; `dataQuality` и `missing`;
причины хард-фильтра; `composite`, число компонентов и `rankTier`; полный
provenance.

**Приёмка.** Рейтинг использует ровно кандидатов оценки · несовместимая оценка
пересчитывается автоматически, и это видно в ответе · все четыре комбинации
фильтров работают · watchlist не скрыт · повтор не вызывает модель заново ·
`POST /ranking/plan` даёт число, совпадающее с фактическим числом вызовов ·
большой прогон без `confirmLargeRun` не стартует · критик применён множителем,
а не слагаемым · строка без score не получает ноль.

**Запрещено.** Требовать включённую alpha. Принимать профиль, расходящийся с
оценкой. Усреднять хард-фильтры. Тихо обрезать выборку. Прятать unrankable и
data-gap survivors.

**СТОП.**

# ШАГ 16 — Отчёты, устойчивость, сквозная приёмка

**Цель.** Доказать, что системой удобно пользоваться, что результат
воспроизводим и что ни один сценарий не требует обхода токенов руками.

### Эндпоинты

- `GET /ranking/latest` — конверт, сводка тиров, watchlist, страница карточек;
- `GET /ranking/report/{runId}` — сохранённый markdown, отдаётся с
  `Content-Type: text/markdown` (markdown внутри JSON-строки нечитаем), путь по
  `runId`, а не по дате: два прогона в один день не должны затирать друг друга;
- `POST /ranking/sensitivity` — 25 пересчётов композита с весами ±30%, без сети
  и без LLM, с интерпретацией: устойчив ли топ к выбору весов;
- `reports/journal.md` — дата, `universeVersion`, полный `activeFilters`,
  `runId` оценки и рейтинга, тиры A/B и композиты. Через 3 и 6 месяцев
  равновзвешенные исследовательские корзины сравниваются с BTC/ETH.

### Основной сценарий

Вселенная уже собрана — работа занимает три запроса:

1. `POST /universe/prices` и `POST /universe/tokenomics` (при необходимости);
2. `POST /universe/screen` и/или `POST /universe/alpha` — или ни одного;
3. `POST /ranking/run`.

Между ними состояние видно в `GET /status`, промежуточные числа — в
`GET /evaluation/latest`. `POST /evaluation/run` нужен отдельно только тогда,
когда хочется посмотреть кодовые результаты до расходов на модель.

Нормальный сценарий не содержит ручного ввода разлоков, ручной загрузки
документов, последовательного запуска трёх компонентов и вызова агентов по
каждому тикеру.

### Сквозная приёмка

- screen on + alpha on → вход оценки равен `status.passed`;
- screen on + alpha off → другой вход, всё работает;
- screen off + alpha on → alpha-only вход, всё работает;
- оба off → оценивается вся вселенная, фильтры не включаются сами;
- три компонента создаются одним POST, сети ноль;
- tokenomics собирается для всей группы одной командой;
- повторная оценка не платит за источники заново;
- повторный рейтинг не вызывает модель заново;
- смена фильтров пересчитывает `sectorPosition` и переиспользует остальное;
- токены без tokenomics и документов видны как data gaps, а не исчезают;
- каждый ответ содержит `universeVersion`, `builtAt`, `activeFilters`, `runId`;
- **открытая руками ссылка подтверждает минимум одно число `valuation`, одно
  событие `tokenomics` и одно `evidence` из `mechanism`**;
- **путь от собранной вселенной до рейтинга — не более 5 запросов**;
- **каждая ошибка 4xx содержит `code` и `nextAction`**;
- **ни один ответ по умолчанию не превышает 300 КБ** (`curl -w`);
- `npm run build` и полный `npm test` зелёные.

### Дисклеймер

Во всех ответах ranking и evaluation и в markdown:

> Исследовательский инструмент. Не является инвестиционной рекомендацией.
> Каждое число проверяется по указанному источнику.

**СТОП. Проект готов.**

## Подводные камни оставшихся шагов

**Оценка не третий фильтр.** `valuation.verdict.passed` и хард-фильтр
tokenomics влияют только на рейтинг и watchlist. Они не меняют `status`, не
подменяют screen/alpha и обязаны сообщать через `appliedBy`, кем проверка уже
была применена.

**Alpha выключена — `sectorPosition` всё равно существует.** Сравнение считается
как оценка и никого не удаляет. Иначе компонент исчезал бы при законной
комбинации фильтров.

**Пустой календарь неоднозначен.** Право сказать `known_zero` есть только у
источника, отдавшего полный календарь. Пустой или непокрытый ответ —
`source_missing`.

**Разлок и эмиссия могут пересекаться.** Источник, отдающий и vesting-события, и
дневную эмиссию, требует доказательства, что это разные потоки. Иначе dilution
удвоится правдоподобно.

**Тикер не идентификатор.** Один символ у двух активов — mapping failure, а не
повод выбрать строку с большей капитализацией.

**Историческое supply не прогноз.** Рост circulating за прошлый год — отдельная
метрика, но не `dilution12mPct` вперёд.

**Кэш LLM не зависит от фильтра.** Смена screen или alpha не оплачивает
повторный `mechanism`, если документы и факты токена те же.

**Большая выборка не запрещена.** При выключенных фильтрах оценка обязана
работать по всей вселенной. Защита нужна только перед дорогими вызовами модели
и обязана показывать `estimatedCalls` **до** попытки старта.

**Ни один компонент не скрывает пробел.** Неизвестная tokenomics, малый сектор
или отсутствие документов отражаются в результате, а не удаляют токен молча.

**Имена совпадают посимвольно.** `sectorPosition` одинаково в типах, весах,
композите и карте рейтинга. Старые `screener` и `unlocks` удаляются одной
миграцией: иначе модуль тихо выпадает из композита, и никто этого не замечает.

**Два тира.** `dataTier` — свойство данных, одинаковое при любом отборе.
`rankTier` — вывод рейтинга. Одно слово на оба — путаница в отчёте и на сайте.

**Профиль без `rationale` — набор чисел.** Через месяц не восстановить, почему
выбран порог. Поле обязательно и едет в отчёт.

**Composite из одного компонента.** Нормировка на сумму доступных весов делает
балл по одному модулю неотличимым от балла по четырём. Число компонентов и
сумма весов едут в карточке рядом с композитом.

## Открытый долг

Не блокирует шаги, но должно быть на виду.

**Ниша ранжируется тремя участниками.** `nft` и `smart-contract-platform` имеют
ровно 3 сравнимых при `minRankedValues: 3`. Один потерянный источник — и ниша
перестаёт ранжироваться. Порог честный, запас нулевой.

**`sectorScore` считается по разному числу метрик.** В `lending` их пять, в
`layer-1` две. Внутри ниши знаменатель одинаков, между нишами баллы и так
несравнимы, но «среднее по доступным» надёжнее там, где доступного больше.

**Метрики коррелируют.** `revenue12mUsd` и `fees12mUsd` — один масштаб, `pRev` и
`pFees` — одна дешевизна. У токена с полными данными масштаб весит вдвое против
доходности держателя. Проверить на первом рейтинге, не перекосило ли топ.

**Признак сети не зависит от категории.** Правило архетипа чинит только `chain`:
Cronos с категорией `dexs` остался в `dexs`, хотя это сеть.

**Подсети Bittensor.** 12 штук, 516 млн, сидят в `ai`. Своей выручки у них нет
по определению — они делят эмиссию TAO. В исключения или в отдельную группу.

**Тир `yield` без порога значимости.** Возникает при любом
`holdersRevenue12mUsd > 0`, включая несущественную сумму. Порог должен быть
явным правилом screen-профиля.

**`tierChanges` в `POST /universe/compare` не несёт информации.** Если тир не
зависит от профиля, поле дублирует `onlyLeft`/`onlyRight`.

**Выручка биржевых токенов не закрывается ни за какие деньги.** 14 токенов;
burn виден на цепи, а выручка приватной биржи не публикуется проверяемо.
Классифицировать burn обязан `mechanism` полем `buybackSource`, код только
измеряет.

**Потолок бесплатного покрытия выручки — около 47 сравнимых.** DeFiLlama
исчерпан по всем восьми `dataType`, Coin Metrics платный, growthepie не
пересекается с составом. Дальше — платный провайдер, интеграция на каждый
проект или ручная документация.

## Что осознанно отложено

Чтобы через месяц не выяснять, потеряно или отброшено.

- **Метрики chain-архетипа** (`networkFees12mUsd`, `feeBurn12mUsd`,
  `issuance12mUsd`, `feeToIssuancePct`): комиссии сети платятся валидаторам, а
  не держателю, и требуют отдельной шкалы. P/Rev для сети не создаётся.
- **Платные провайдеры** (Token Terminal, Artemis, Dune, DeFiLlama Pro):
  подключаются как опциональные адаптеры второго уровня, ни один шаг от них не
  зависит.
- **Дробление `mechanism` на несколько вызовов**: если модель путает категории,
  схема делится по смыслу, а не уговаривается промптом. Один большой вызов
  заполняется хуже нескольких малых.
- **Аутентификация и мультипользовательский режим**: до переезда на сайт
  сервис однопользовательский, и `ActiveFilterState` глобален. На сайте это
  первое, что придётся разделить по пользователям.
